MLOps on Snowflake

A data-science team develops in a governed sandbox inside a production account, then ships a model through an automated, approved pipeline.

Overview

The lifecycle

A model moves left to right: explore production data and shape it into features, train and compare versions with tracked experiments, then promote the best one to production through a keyless, approved pipeline — after which it serves predictions on a schedule.

1 · ExploreRead production data, build a clean base table, and define the features the model will use.
2 · RetrainAdd a feature, retrain, log the run to an experiment, and compare the new version to the current one.
3 · DeployPromote the winning model to production through a gated CI/CD pipeline — no manual deploys.
The governance boundary is on deployment: the sandbox can read all of production, but only an approved, automated service account can write to it.

The data

IBM AML — anti-money-laundering transactions

A labeled, multi-bank transaction dataset: money moving between accounts across many banks, with a small share flagged as laundering. It sits at the very start of the pipeline — the raw material every feature and model is derived from.

What each record contains

Every transaction has an amount, a paying and receiving currency, a payment format (ACH, wire, cheque, card, etc.), the sending and receiving accounts and their banks, and a timestamp. A binary IS_LAUNDERING flag marks the illicit ones, and a companion set describes the laundering typologies — fan-out (one account spraying funds to many), structuring (splitting a large sum into many small ones), and cycles (money routed in a loop back to its origin).

Why it fits this use case

Anti-money-laundering is fundamentally rare-event detection: only a tiny fraction of activity is illicit, and it hides inside enormous volumes of legitimate traffic — exactly the shape of this data. Because transactions span many banks and borders, the behaviors launderers create — bursts of activity, spreading funds across many receivers, mixing currencies — are actually observable in the data, which is what makes them learnable as features.

How the model is measured

With positives near 0.1%, accuracy is meaningless (a model that predicts "never" is 99.9% accurate and catches nothing). We use PR-AUC and recall@1% — the share of true laundering captured in the top 1% of scored transactions, which mirrors the limited alert budget an investigations team really works with. Training and evaluation use a chronological split (train on earlier activity, test on later), reflecting how the model scores the future in production.

Step 1

Explore & transform

The data scientist's first move: rather than building features directly on raw tables, they explore production, then apply a selective transform that turns raw events into a clean, labeled analytical base table. Feature views — reusable, governed feature definitions — are built on top of it.

On screen

  • A look at production data — for example, the laundering rate broken out by payment channel.
  • Building the base table from production: read-only on prod, written into the sandbox.

The features and what they capture

Request context — describes the transaction in front of us: the amount, whether it crosses currencies or borders, whether the payment format is high-risk, and how the amount compares to the account's own typical spend. These are the "what is happening right now" signals.
Account profile — a behavioral fingerprint built from each account's history: its typical and maximum amounts, how volatile its spending is, and how many distinct receivers, banks, and countries it interacts with. A brand-new account with no history looks very different from an established one — which itself is a signal.

Because these are defined once in the feature store, the exact same feature logic is reused for training and for scoring — and the same transform runs later in production during promotion, so dev and prod build features identically.

Also on Snowflake (beyond this step): the same feature store can serve features online for real-time scoring, and can generate point-in-time-correct training sets so a model only ever sees data that existed at each moment.

Step 2

Add a feature, retrain, compare

The iteration loop: register a new feature view, retrain the model, log the run to an experiment, and compare the new version against the current baseline — all inside the sandbox.

On screen

  • A new feature view registered from account history.
  • A retrain to V2, captured as an experiment run, with a printed V1 → V2 comparison.

The new signals — and why they matter

Spend volatility — how erratic an account's transaction amounts are relative to its own norm. A steady payer has low volatility; an account suddenly moving unusual amounts stands out.
Receiver fan-out — the number of distinct receivers relative to how many transactions an account makes. An account spraying funds across many different destinations is the classic "mule" pattern in a fan-out typology. This feature is constrained so that more fan-out can only raise the risk score, never lower it.

How the model works

It's a gradient-boosted tree model, weighted to handle the extreme class imbalance, with monotonic constraints so that risk-increasing signals (amount, cross-border, fan-out, …) can only push the score up. Every run's parameters and metrics are recorded in experiment tracking, giving an auditable before/after: adding these two signals measurably improves the model (higher PR-AUC and recall@1%), and the winning version becomes the promotion candidate.

Also on Snowflake: distributed training and hyperparameter tuning across a compute pool, and ongoing model monitoring / drift detection once a model is in production.

Step 3

Promote to production

Promotion is a packaged job that runs server-side as the service account, triggered through GitHub with a required approval. A data scientist cannot deploy by hand — the pipeline does it for them, under sign-off.

What runs where

GitHub ActionsTriggers the deploy, authenticates to Snowflake with a keyless token, waits for an approver, and submits the job.
Snowflake computeAn ML Job runs the promotion server-side on a compute pool, then tears itself down — disposable compute for a one-off task.

The gate — all four apply

  • Access control — only the service account can write production; the data scientist role is blocked by privileges.
  • Keyless identity — GitHub mints a short-lived token that Snowflake accepts only from this repository's production context. There's no key or password stored to leak.
  • Human approval — a designated reviewer must approve each deploy in GitHub before the job runs.
  • Auth policy — the service account is restricted to workload-identity authentication only.

What promotion actually does

  • Rebuilds the production base table using the same transform written in dev (so features match exactly).
  • Promotes the exact trained model into the production registry — it ships the artifact, it does not retrain.
  • Registers the production feature views and creates the scheduled batch scoring task.
Promotion runs once per release. The recurring work is separate: a daily scoring task and auto-refreshing feature views keep producing predictions with no human and no job in the loop.
Also on Snowflake: the same pattern extends to scheduled retraining pipelines and, when low latency is needed, real-time inference endpoints served from the online feature store.

Beyond this demo

The same platform also supports capabilities we're not showing today:

  • Online / real-time serving — a Postgres-backed online feature store with millisecond point lookups and sub-2-second stream freshness, for real-time scoring instead of scheduled batch.
  • Model monitoring & drift — track a model's performance and input drift over time once it's live in production.
  • Distributed training & tuning — train larger models and search hyperparameters across a compute pool.
  • Lineage — trace a prediction back through model, features, and source data for audit and impact analysis.
